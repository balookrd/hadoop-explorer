# Чек-лист настройки боевых кластеров для HMS-репликации

Что проверить на кластерах-источниках и приемниках (HDP 3.1 / Hive 3.1, Kerberos) до первой задачи репликации схем. Пункты идут в порядке, в котором их удобно проверять: идентичность, метастор, HDFS, DML, оркестратор и агенты, пробный запуск.

Обозначения:

- **учетка агента** — Kerberos-принципал из keytab агента (`KRB5_PRINCIPAL`, например `replicator/host@REALM`), в Hadoop — короткое имя после `auth_to_local` (например `replicator`);
- **пользователь задачи** — `execution_principal` задачи: от его имени метастор создает базы, таблицы и каталоги, и от его же имени пишутся данные на приемнике.

---

## 1. Kerberos и учетка агента

- [ ] У каждого агента есть keytab с принципалом агента; файл читается пользователем, под которым работает агент, и только им.
- [ ] `KRB5_PRINCIPAL` и `KRB5_KEYTAB` (или `REPLICATOR_KEYTAB_PATH`) заданы; `kinit -kt <keytab> <principal>` на узле агента проходит.
- [ ] `krb5.conf` на узлах агентов знает оба realm (если кластеры в разных) и их KDC.
- [ ] Время на узлах агентов синхронизировано с KDC (расхождение больше 5 минут — `Clock skew too great`).
- [ ] `auth_to_local` на обоих кластерах переводит принципал агента в ожидаемое короткое имя.

Агент сам обновляет TGT по keytab перед открытием соединений с метастором и выдачей delegation token: срок жизни билета (обычно 10–24 ч) bootstrap не ограничивает.

## 2. Имперсонация: агент действует от имени пользователя задачи

Метастор создает каталоги баз и таблиц от имени пользователя задачи (doAs), а данные на приемнике пишутся от того же пользователя. Агент для этого действует как proxy-пользователь.

- [ ] **HDFS, оба кластера** (`core-site.xml` NameNode):
  ```xml
  <property><name>hadoop.proxyuser.<учетка агента>.hosts</name><value>узлы агентов</value></property>
  <property><name>hadoop.proxyuser.<учетка агента>.groups</name><value>группы пользователей задач</value></property>
  ```
- [ ] **Hive Metastore, оба кластера** (`core-site.xml` метастора): то же право для учетки агента — без него метастор не выдаст delegation token пользователя (`User: ... is not allowed to impersonate ...`).
- [ ] **HDFS, оба кластера**: право proxy для учетки `hive` (метастор с doAs создает каталоги от имени вызывающего) — на HDP обычно уже есть.
- [ ] После правки `core-site.xml`: `hdfs dfsadmin -refreshSuperUserGroupsConfiguration` на NameNode, перезапуск метасторов.

Без этих прав агент получает `Permission denied` при записи в каталог, созданный метастором от имени пользователя, а на HDP с суперпользователем `hdfs` ошибка не видна, но владельцем файлов на приемнике становится служебная учетка.

## 3. Права пользователя задачи

- [ ] На источнике пользователь задачи читает каталоги переносимых таблиц и партиций.
- [ ] На приемнике пользователь задачи пишет в каталог warehouse базы назначения (или в родительский каталог, если базы еще нет).
- [ ] Если включен Apache Ranger: политики HDFS и Hive для пользователя задачи на обоих кластерах; для учетки агента — право на метастор (`get_delegation_token`, чтение журнала событий).

## 4. Hive Metastore источника

- [ ] Журнал событий включен (`hive-site.xml` метастора):
  ```xml
  <property><name>hive.metastore.transactional.event.listeners</name>
            <value>org.apache.hive.hcatalog.listener.DbNotificationListener</value></property>
  ```
- [ ] Срок хранения событий `hive.metastore.event.db.listener.timetolive` больше самого долгого ожидаемого bootstrap и простоя задачи (по умолчанию 86400 с = 1 сутки). Для схем с таблицами на сотни тысяч партиций — с запасом в несколько раз.
  Если события удалены раньше, чем агент их прочитал, задача переходит в `ERROR` с требованием повторного bootstrap — продолжить CDC через разрыв журнала нельзя.
- [ ] Чтение журнала разрешено учетке агента: `hive.metastore.event.db.notification.api.auth=false` или учетка агента в списке прокси метастора.
- [ ] Метастор-приемник может работать без журнала событий, но обязан принимать учетку агента как proxy (п. 2).
- [ ] База метастора-источника — MySQL, PostgreSQL или Oracle, но не Derby. На Derby метастор не блокирует счетчик событий, при параллельных DDL-клиентах в журнале появляются события с одинаковыми номерами, и клиент Hive 3.1 видит в этом пропуск: задача уходит в `ERROR` с требованием повторного bootstrap. Несколько экземпляров метастора на одной базе допустимы для Hive 3.0+ (в HDP 3.1 счетчик блокируется).

Агент работает с клиентом метастора Hive 3.1 и понимает формат событий `json-0.2` (Hive 3 / HDP 3.1) и `gzip(json-2.0)` (Hive 4).

## 5. Дозапись данных в существующие партиции (без inotify)

Новые таблицы и партиции переносятся по событиям `CREATE_TABLE` / `ADD_PARTITION`. Дозапись в существующую партицию видна агенту только по событию `INSERT`.

- [ ] В HiveServer2 (и в любом Hive-клиенте, выполняющем DML) включено `hive.metastore.dml.events=true` — по умолчанию `false`, и событий `INSERT` в журнале нет.
- [ ] **Spark событий `INSERT` не публикует.** Дозапись Spark в существующие партиции без inotify не переносится: для таких таблиц нужен HDFS-стриминг (inotify) или повторный bootstrap.
- [ ] `INSERT OVERWRITE`: агент удаляет на приемнике файлы, которых больше нет в каталоге партиции, — учтите это для каталогов, куда на приемнике пишут что-то еще.

ACID-таблицы (`transactional=true`) не переносятся по ТЗ и помечаются в журнале задачи как `SKIPPED_ACID`.

## 6. HDFS-стриминг (inotify) — второй этап

Задача с `enable_hdfs_streaming=true` заводит подзадачу-компаньон на каталог базы в warehouse. Стример читает журнал правок NameNode источника и переносит файлы, о которых метастор не знает (дозапись из Spark).

- [ ] На кластере-источнике запущены стримеры (`AGENT_MODE=streamer`, два для отказоустойчивости: активный выбирается арендой в оркестраторе).
- [ ] Принципал стримера — **суперпользователь HDFS**: член группы `dfs.permissions.superusergroup` на NameNode источника. Журнал правок (`getInotifyEventStream`) другим не отдается.
- [ ] Срок хранения журнала правок NameNode (`dfs.namenode.num.extra.edits.retained`, `dfs.namenode.max.extra.edits.segments.retained`) покрывает самый долгий простой стримера. При разрыве журнала стример сверяет каталоги заданий целиком.
- [ ] Таблицы, данные которых лежат вне каталога базы (внешние таблицы с собственным `LOCATION`), стримингом не покрываются: компаньон следит только за каталогом базы.
- [ ] Удаления компаньон переносит только по флажкам сверки задачи. «Удалять лишние таблицы» разрешает удалять каталоги таблиц (первый уровень под каталогом базы). «Удалять лишние партиции» разрешает удалять все внутри таблиц: каталоги партиций и файлы, вытесненные перезаписью (`INSERT OVERWRITE` из Spark). Вынос в корзину (`.Trash`) считается удалением. Без флажков на приемнике ничего не удаляется, и после перезаписи старые файлы остаются рядом с новыми. Каталог базы не удаляется никогда. Каталоги приемника, куда пишет кто-то еще, в задачу с удалениями не включайте.
- [ ] Пауза задачи останавливает перенос. После возобновления стример переносит файлы, измененные за время паузы, и удаления, сделанные на паузе (если их разрешают флажки). Путь, созданный заново, не удаляется. Удаления с паузы стример держит в памяти, до 100 000 путей на задачу. Если активный стример сменится, пока задача на паузе, они потеряются, и удаленные файлы останутся на приемнике до следующего bootstrap.

## 7. Оркестратор

- [ ] База — PostgreSQL (не H2): `SPRING_DATASOURCE_URL`, учетка с правами на схему. Миграции Flyway применяются при старте (проверены на PostgreSQL 16).
- [ ] Для отказоустойчивости — два и более узла на одной базе; агенты знают все узлы (`ORCHESTRATOR_GRPC_ADDRESSES=узел1:50050,узел2:50050`).
- [ ] `HADOOP_REPLICATOR_AGENT_SECRET` одинаков на всех узлах и агентах.
- [ ] `HADOOP_REPLICATOR_HMS_MAX_BOOTSTRAPS_PER_AGENT` (по умолчанию 4) — сколько bootstrap один агент ведет одновременно; CDC-задачи раздаются без предела с выравниванием по агентам.
- [ ] Порог OFFLINE агента (`agent-offline-timeout-seconds`, 45 с) и аренда HMS-задачи (`HADOOP_REPLICATOR_HMS_LEASE_TIMEOUT_SECONDS`, 30 с) — по умолчанию подходят.

## 8. Агенты

- [ ] Клиент метастора — Hive 3.1 (входит в сборку агента), `HMS_THRIFT_URIS` указывает на метастор своего кластера, `HMS_KERBEROS_PRINCIPAL` — его сервисный принципал.
- [ ] `REPLICATOR_FEDERATION_MAPPINGS` / `TARGET_HDFS_DEFAULT_FS` переводят пути источника в пути приемника для всех nameservice, где лежат таблицы (иначе таблица помечается как без сопоставления и не переносится).
- [ ] Барьер «данные раньше DDL» включен (`REPLICATOR_HMS_DATA_BARRIER_ENABLED=true`), таймаут `REPLICATOR_HMS_DATA_BARRIER_TIMEOUT_SEC` (по умолчанию 6 ч) больше времени копирования самой большой порции из 1000 партиций.
- [ ] Куча агента — от 1 ГБ: обход партиций идет порциями по 1000, на стенде агент держал таблицу в 200 000 партиций в 512 МБ.
- [ ] `ANALYZER_CONCURRENCY` (по умолчанию 8) — сколько подзадач копирования агент анализирует параллельно. С барьером данных CDC заводит подзадачу на каждую новую партицию; на стенде 8 потоков давали 40–80 подзадач в секунду на агента-источника.

## 9. Пробный запуск

1. Задача на небольшую базу (несколько таблиц, сотни партиций), без inotify. Проверить: статус `ACTIVE`, число партиций и формат хранения на приемнике, владелец файлов — пользователь задачи.
2. На источнике: `ALTER TABLE ... ADD PARTITION`, `INSERT INTO` в существующую партицию (через HiveServer2 с `dml.events`), `DROP PARTITION` — изменения доходят до приемника за минуту, в журнале задачи события `APPLIED`.
3. Пауза и возобновление задачи из UI; остановка агента посреди bootstrap — после возврата перенос продолжается с чекпоинта.
4. Только после этого — большие схемы.
5. Второй этап (inotify): задача со стримингом на небольшую базу; дозапись файла в существующую партицию без `INSERT` и перезапись партиции из Spark доходят до приемника, на приемнике не остается старых файлов.

Сценарии стенда, на которых все это проверено, — в `demo/replicator/README.md`: нагрузочный прогон на 200 000 партиций, совместимость с HMS 3.1, рой из 200 агентов, живые `INSERT`, отказы узла оркестратора и агента, CDC на нагруженном метасторе, HDFS-стриминг HMS-задачи.
